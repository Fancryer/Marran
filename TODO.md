## P1 — язык

### P1-1, P1-2. Стандартная библиотека

Нужно потихоньку реализовать stdlib по сигнатурам из `app/std.marr`:
`Functions`, `Numbers`, `Strings`, `Booleans`, `Arrays`, `Pairs`, `Output`,
`Input`, `Conv`, эффекты `Env`, `File`, `Random`, `Time`, `System`, `Error`.

Как: каждое имя из рекорда получает схему в `Scope.globalScope` и значение в
`IntInterpreter.buildInitialEnv` (нативная операция) или в библиотеке на самом
Mårran. Ссылки на функции из рекордов продублировать в глобальной области, чтобы
не писать `Numbers@+`, `Numbers@to_float`. `Builtins.builtins` сверяет два
списка, поэтому имя, добавленное с одной стороны, диагностируется сразу.

Закрыто по сигнатурам `app/std.marr`: `Numbers`, `Strings`, `Booleans` (имена и
напрямую, и через запись — запись это вид на те же значения), `Functions`,
`Arrays`, `Pairs`, `Conv@show`, `Output`, `Input`, `Error@try`/`Error@assert`,
эффекты `Env`, `File`, `Random`, `Time`, `System`.

Как закрыт вопрос полиморфных полей: `inferRecord` выводит поля записи
мономорфно, поэтому `Functions`/`Arrays`/`Pairs`/`Conv` распакованы — имена
живут в `Scope.polyEntries` (схема + `openArrows`) и в `buildInitialEnv`
(нативное замыкание), а `Builtins.builtins` перечисляет их как обычные
builtin'ы. Рекорд с полиморфным полем появится тогда, когда `inferRecord`
научится схеме поля; до тех пор плоское имя — не второй API, а единственный, а
рекорды `Numbers`/`Strings`/`Booleans` строятся из тех же адресов.

Закрыто и `Conv@parse`: имя объявлено `BuiltinKind.TypeDirected` — проверка
типов видит его полиморфной схемой `String -> {Error} `T` и требует `with`, а
интерпретатор получает представление типа (`TypedIR.TypeRep`) скрытым первым
аргументом и строит по нему значение. Подробности — P1-4 ниже.

### P1-5. `match ... to ...`, `enum`

Закрыто; см. «Проверено и закрыто». Грамматика, по которой делалось
(ANTLR, от Алисы):

```
match_to: 'match' block 'to' match_clause+;

match_clause: ('|' pattern ('if' exp)? | primitive_clause ('as' Name)?) '=>' block;

primitive_clause: '|' (int+ | float+ | string+);

pattern:
  int                                               #int_pattern
  | float                                           #float_pattern
  | string                                          #raw_str_pattern
  | <assoc=left> left=pattern '<-|' right=pattern   #str_ends_with_pattern
  | <assoc=right> left=pattern '|->' right=pattern  #str_starts_with_pattern
  | nil                                             #nil_pattern
  | boolean                                         #boolean_pattern
  | Name                                            #name_pattern
  | 'val' (Name | path_exp)                         #val_pattern
  | arr_pattern                                     #array_pattern
  | <assoc=right> left=pattern ',' right=pattern    #tuple_pattern
  | '#' con_pattern                                 #constructor_pattern
  | pattern 'as' Name                               #alias_pattern
  | pattern ':' type                                #cast_pattern
  | '_'                                             #wildcard
  | '(' pattern ')'                                 #paren_pattern
  ;

con_pattern
  : Name          #singleton_constructor
  | Name nil      #empty_constructor
  | Name patterns #non_empty_constructor
  ;

arr_pattern
  : '[' ']'                                                 #empty_array
  | '[' head=pattern body=patterns? (';' tail=pattern)? ']' #non_empty_array
  ;

patterns: pattern+;
```

Алгебраические типы:

```
enum_def: 'enum' Name type_params? eff_params? enum_case+;
enum_case: '|' Name ('(' constant_qualifier? Name (':'? type)? ')')?;
```

Энум — несколько конструкторов, у каждого может быть квалификатор мутабельности;
без квалификатора — `val`:

```
enum Maybe[T] | None | Some (value `T)
```

### P1-6. Модули и `import`

P1-6 закрыт: шаг 1 (заголовок `module`) — ветка `0.2-beta`, шаг 2
(импорты) — ветка `0.2.2-beta`.

**Шаг 1: заголовок.** `src/Module.hs` — `Module d {modHeader, modDecls}`
(`Functor`/`Foldable`/`Traversable`), `ModuleHeader {mhName, mhExports,
mhSpan}`, `ExportDecl {edSpan, edKind, edName, edAlias}`, `DeclKind =
KindFunct | KindType | KindEffect | KindRow | KindEnum`, `headerExportsAll`.
`Ast.Chunk`, `Types.Chunk` и `TypedIR.Chunk` — один и тот же type synonym
`Module <свои TopLevelStat>`, поэтому заголовок едет через все фазы без
side-канала. `Ast` реэкспортирует `module Module`; `declKindOf` живёт в `Ast`
(он про `TopLevelStat`).

Лексер: `KWModule`, `KWImport` (второе пока не разбирается — задел на шаг 2).
Парсер: `chunk` требует `module Name`, затем необязательный
`[decl ...]`, затем объявления до `eof`; `exportDecl` собирает span, необязательный
вид, имя и `as`-алиас. Файл без заголовка — E0013 с текстом «a file must start
with a module header», а не «unexpected `funct`»: это первая ошибка, которую
делает читатель, когда заголовок стал обязательным.

Проверка: `elaborate`, `inferChunk` и `evalChunk` разбирают `Module header ds`
и собирают его обратно; `findMain` и `mainSpan` принимают `Chunk` целиком.

Миграция: `module Main` первой строкой во всех 25 `app/marr/*.marr` и в
`app/*.marr` (включая устаревшие `main_*.marr`, `infer.marr`, `std.marr` —
их всё равно не парсит старый синтаксис). Инлайн-тесты не правились:
`Suite.withModuleHeader` добавляет `module Main` прямо перед первой строкой
(и пропускает `//|`-комментарии сверху), поэтому номера строк в тестах не
сдвинулись. `runProgram` (файл с диска) заголовок не добавляет — иначе
обязательность была бы фикцией.

`SpanSpec` проверяет и `mhSpan` заголовка. `ParserSpec` — новый блок
«the module header»: отсутствие заголовка, имя, отсутствие списка экспорта,
виды и `as` в списке, ключевое слово вместо имени.

**Шаг 2: импорты** — сделан, ветка `0.2.2-beta`.

```
module name [d1 ... dn]

import a                       //| всё, что экспортирует a
import a#i1                    //| одно имя (сахар для a [i1])
import a [i1 ... in]           //| перечисленные
import 'dir/' [a b]            //| вложенная структура: a и b из dir
import @native Numbers         //| виртуальный нативный модуль
import @native                 //| весь нативный скоуп

d1
...
dn
```

`d1 ... dn` — список экспортируемых объявлений: функции, эффекты, энумы, алиасы
рядов и типов. Точки с запятой не нужны. Если два объявления носят одно имя, в
списке экспорта перед именем пишется вид: `funct/enum/type/effect/row/...`.
`i1 ... in` — импортируемые объявления другого модуля. Модули вычисляются
нестрого и поддерживают взаимно рекурсивные импорты.

**Энум приходит с конструкторами.** Назвать энум в списке экспорта или
импорта — значит назвать и его значения: `import a [enum Colour]` ввозит
`Colour` и `Red`/`Green`, отдельно их перечислять не нужно (и можно: повтор
одной и той же записи — не столкновение). Обратное неверно: `#Red` без
`Colour` — обычная ошибка «нет такого конструктора». `as` переименовывает
**тип** (`enum Colour as Shade` — это `Shade` в сигнатурах), но не значения:
имя конструктора — не имя типа, и `Shade.Red` язык не умеет. Переименование
типа достаёт и до конструктора: его схема начинает говорить `Shade`, иначе
`c Shade` не совпал бы с `Red`. Два энума с одним конструктором в одном
пространстве имён — статическое столкновение; клапан — назвать конструктор
явно и переименовать: `[enum Shade funct Red as Crimson]` (названный явно
конструктор не добавляется вторым, поэтому `Red` остаётся за первым энумом).

**Переименование достаёт до тела объявления.** `as` — это не только новое имя
в таблице: все типы, которые объявление называет, тоже переписываются, иначе
объявление говорит на языке модуля-объявителя, а импортёр такого имени не
знает. Переписываются схемы функций и конструкторов, поля энума, сигнатуры
операций эффекта вместе с их рядами (`effect Writer out : Mode -> ()` при
`enum Mode as Speed` называет `Speed`), и тело типового алиаса в элабораторе
(`type Colours = [Colour]` при `enum Colour as Shade` — это `[Shade]`). Рядовые
алиасы (`row`) переписываются так же. Переменные типа (`[T]`) не трогаются:
это не имена объявлений.

**Загрузчик** (`src/Loader.hs`). `loadText` разбирает первый файл, читает
импорты, ищет файлы и строит граф, затем `resolveGraph` отвечает на два
вопроса: какие имена модуль видит и какие предлагает. Граф режется
`Graph.stronglyConnComp` — он уже отдаёт компоненты в порядке зависимостей.
Одиночный модуль читает таблицы уже устоявшихся предшественников; цикл
(`CyclicSCC`) растёт до неподвижной точки (`grow`: `publishOf` на каждом шаге,
`Map.union` с уже известными), после чего строгий проход (`strictPublish`,
`strictVisible`) отчитывается о том, что так и не появилось. Таблица —
`Map Text [Imported]`: одно имя может быть объявлено дважды (`funct f` и
`type f` — это две декларации одной записи, их различает позиция, как и в
одном файле), поэтому под именем лежит список, по одному `Imported` на
пространство имён. `Imported` помнит **модуль-объявитель** (`FromModule path`
/ `FromNative m`), поэтому имя, прошедшее через реэкспорт, приходит из того
модуля, где написано, а не из середины цепочки. `Program` хранит `progUnits`,
`progSources` и `progEntry`; `Unit` — это `unitPaths`/`unitModules`, то есть
цикл не склеивается в один чанк, у каждого модуля свои объявления и свои
таблицы.

**Вид в списке — это пространство имён.** Голое имя в списке экспорта или
импорта ввозит все декларации этой записи; `[type f]`/`[funct f]` — только
одну. Вид, которого у источника в этом пространстве нет, — ошибка про вид, а
не про запись: «`cell` is a function in func.marr, not a type». Затенение тоже
по пространствам: своя `funct f` перекрывает импортированную `funct f`, но
импортированная `type f` всё равно приходит. Импорт, назвавший имя, которого
у источника нет, падает на строке импорта (`strictImport`), а не `E0007` у
использования: «`nosuch` is not offered by the module `lib.marr`» с запиской
«it offers: one» либо «declared in lib.marr but not exported».

Здесь же проверяется, что запускаемый файл говорит `module Main`: имя модуля с
именем файла не сверяется, но файл с другим заголовком — библиотека, и `--run`
отвечает «`X` is a library, not a program».

**Парсер**: `chunk` разбирает `module Name`, необязательный список экспорта,
затем `many importDecl` (то есть импорты только сразу после заголовка) и
объявления до `eof`. `importDecl` знает `#`, список в скобках, `'dir/'`-группу
и `@native`; `import @native` без имени — весь нативный скоуп.

**Элаборатор** (`elaborateProgram`): каждый модуль получает свой `RowEnv` и
`TypEnv` — свои объявления плюс типы/ряды/эффекты, которые пришли по импорту.
`importedDecls` идёт по `mhResolved` в модуль-объявитель и берёт оттуда
`TypeDef`/`EnumDef`/`RowDef`/`EffectDef`; приватный алиас другого модуля в
`TypEnv` не попадает вовсе.

**Проверка типов** (`inferProgram`, `inferModule`): у каждого модуля свой
скоуп — нативные имена только импортированных модулей (`Scope.nativeScope` по
фильтру), затем импортированные модули по таблице, затем свои объявления
(`enterScope` даёт изоляцию, `addBinding`/`addEnum`/`addEffect` наполняют её).
`Interface` — то, что модуль предлагает: схемы функций, энумы, эффекты; для
цикла он берётся из объявлений (`declaredInterface`), потому что «первого»
модуля в цикле нет. Конструкторы энума — обычные значения, поэтому в
`Interface.inValues` они входят наравне с функциями.

**Интерпретатор** (`interpretProgram`): у каждого модуля своё `EnvId` с
родителем — корневым окружением нативов. Сначала свои объявления
(`evalModule`), потом копируются адреса импортированных имён
(`linkImports`): одна функция на программу, а два приватных `helper` в двух
модулях — это два адреса в двух окружениях. Модули цикла получают окружения до
того, как заполнены, и `linkImports` видит уже всю единицу, поэтому взаимная
рекурсия работает. Запускается только `main` из `progEntry`.

Решения по шагу 2 (как реализовано):

- **Модуль — один файл**, `import a` ищет `a.marr`: сначала рядом с
  импортёром, затем `app/marr/`, затем `app/`. Ошибка перечисляет, где искали,
  и `.marr` не удваивается. Имя с разделителем пути ищется рядом с импортёром
  и как написано, без похода в `app/marr`.
- **Имя модуля свободно**: с именем файла не сверяется; запускается только
  `module Main`, остальное — понятная ошибка «это библиотека».
- **Все имена импортируются голыми**; `a@f` после импорта не работает (нет
  квалифицированного доступа). `import @native` — тоже группа голых имён.
- **Настоящая приватность**: модуль видит свои объявления и импортированные,
  и ничего больше; список экспорта действительно скрывает (per-module env, а
  не один плоский скоуп). Два приватных `helper` в разных модулях — норма,
  это разные имена и разные адреса.
- **Один экземпляр модуля** на программу; **top-level `val`/`var` в модуле
  запрещены** — только объявления, состояние через параметры и эффекты.
- **Столкновение имён** — статическая ошибка с указанием обоих модулей;
  алиасы `import a [d1 as n1]` — клапан. Своё объявление перекрывает импорт
  (перекрытый импорт просто не попадает в таблицу, а не жалуется).
- **`as` работает для всех пяти видов**, и в экспорте (переименование для всех
  импортёров), и в импорте.
- **`import` только сразу после `module`**.
- **SCC — одна единица проверки**: типовые объявления цикла читаются вместе,
  наружу — объединение экспортов; порядок SCC топологический.
- **Реэкспорт разрешён**: список экспорта может назвать импортированное имя;
  без списка экспортируется всё объявленное и всё импортированное.
- **Нативные модули вместо рекордов**: `import @native Numbers` и т.д.;
  поверхность — в `docs/stdlib.md`; `app/std.marr` удалён. Без
  `import @native` нативные имена не видны вообще (E0007).
- **Эффекты — в нативных модулях** вместе с операциями: `Output`, `Error`,
  `Env`, `File`, `Random`, `Time`, `System`.
- Директивы `$std`/`$native`/`$my_precious`, `morko_part` (`Name '@'`),
  `concrete_module_path` (`'path':`) и `marr.ilyn` — отдельный пункт после
  P2-1: сейчас интерфейс не задан, и угадывать пути хуже, чем честно сказать
  «директива не настроена». `morko_part` и `concrete_module_path` не парсятся
  намеренно.

**`M::x` (0.2.3.1).** Квалифицированное имя работает во всех пространствах:
типы и их аргументы, эффекты, ряды, значения, конструкторы и операции
эффектов. Часть модуля — имя из заголовка импортированного файла или базовое
имя файла; имя должно быть экспортировано и принесено списком импорта.
Типы, ряды, эффекты и аргументы типов переписываются в локальное написание
импорта, конструкторы в образцах — в объявленное имя, значения и конструкторы
получают отдельные привязки (`mhQualified`), поэтому локальный `let` их не
перекрывает, а объявление верхнего уровня, перекрывающее импорт, — диагностика.

## P2 — интерпретатор и инструменты

### P2-1. Конфигурация в `marr.av`

`Config.hs` нигде не используется: `app/Main.hs` его не импортирует, а конфиг
ищется как `marr.ilyn` / `~/.config/marr/marr.ilyn`. Решение: доработать
`Config.hs` так, чтобы конфигурация интерпретатора описывалась в `marr.av`, и
подключить загрузчик в `Main`.

### P2-2. Печать значений

Закрыто. Функция печатается своим именем (`add1`, `+`), стадия частичного
применения — `<partial: add>`, лямбда — `<lambda>`, `trace` показывает значение.
См. «Проверено и закрыто».

### P2-3. Запуск по абсолютному пути

Закрыто. `--run` принимает путь к файлу (в том числе абсолютный) и имя из
`app/marr`. См. «Проверено и закрыто».

### P2-4. Нативные лямбды не нужны

Закрыто. `TENLambda` в интерпретаторе недостижим: значение нативной функции
лежит в нативном скоупе, выше пользовательского глобального, а `TENLambda` в
биндинге нужен только проверке типов, чтобы назвать тип имени. Ветка теперь
говорит именно это («internal error: a native signature reached the
interpreter as a value»), а не «not implemented», и `val f = +; f 1 2`
работает.

### P2-5. `read_string` требует кавычек

Закрыто: `read_string` читает строку целиком, как её ввели. См. «Проверено и
закрыто».

### P2-6. Предупреждения сборки

`stack build` даёт `-Wunused-top-binds`, `-Wunused-imports`, `-Wduplicate-exports`
и т.п. Часть почищена; остальное — по мере касания файлов.

### P2-7. `stack.yaml` — источник истины

Явный `hpack` не нужен. `stack.yaml` — источник истины; `Marran.cabal` не
поддерживать вручную ради расхождения с `package.yaml`.

## Бэклог

- **Трамплин / дефункционализация.** Кучи больше нет (она в Haskell), но
  живая память всё ещё растёт с числом хвостовых вызовов: CPS-интерпретатор на
  `callCC` оставляет Haskell-кадр на каждый вызов, а в нём окружение вызова.
  Замер: `loop n 0` — ~300 Б на итерацию на одну переменную цикла, ~600 Б на
  две. Поэтому `+RTS -M64m` обрывает цикл на несколько сотен тысяч шагов, хотя
  без ограничения проходят десятки миллионов. Лечится только переводом
  `evalExpr`/`evalBlock`/применения функции на машину с явными продолжениями
  (заново: `callCC`, обработчики, `resume`) — то есть новый интерпретатор;
  отдельная задача, не блокирует язык и stdlib.
- **Полиморфные операции в `EffDef`.** Параметры эффекта сейчас — это `Taste`
  (жёсткие переменные), и применение эффекта подставляет в операции именно их:
  `effect Ask[T] ... ask : () -> `T` работает для любого `T`, потому что `T`
  один и тот же в объявлении и в применении. Но операция не может быть
  полиморфной сверх параметров эффекта: `effect Store[S] push : `T -> ()`
  не выразить — схемы у операции нет, `EffDef` хранит `[Taste]` и `Funct`.
  Когда понадобится, `EffDef` получит схему операции и своё квантование.
- **Арность применения эффекта проверяется в ряду.** Правило: применение
  эффекта сверяется с объявлением там, где эффект написан (`{Loop}` вместо
  `{Loop#[Int]}` — ошибка в строке ряда), а не в момент вызова операции.
  Так и сделано в `elaborateEffCons`; при этом `inferHandler` и
  `instantiateOps` тоже проверяют арность, потому что `under` приходит не
  через ряд. Если появится третий путь, через который эффект входит в
  программу, проверку надо будет переиспользовать, а не копировать.
